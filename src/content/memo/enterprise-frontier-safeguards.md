## はじめに

2026年9月1日に Claude Fable 5.1 と Claude Mythos 5.1 が発表されました。性能や価格の話題に混じって、Enterprise Frontier Safeguards（EFS）という新しい仕組みが紹介されています。

https://www.anthropic.com/claude-fable-and-mythos-5-1

一言でいうと、EFS は「データを Anthropic に残さない」ことと「悪用を見つけるための監視」を両立させる仕組みです。言われてみれば相反する要求に見えるので、どこで両立させているのかが気になりました。

この記事では、EFS がどういう構造で動いていて、なぜ安全に使えると言えるのかを図で整理します。

本記事は2026年9月2日時点の公式発表をもとに書いています。EFS は2026年の秋から段階的に提供される予定で、細かな仕様は今後変わる可能性があります。
:::

## EFS とは何か

EFS は、Fable 5.1 のような Mythos クラスのモデルを企業が使うための安全装置で、監視に使うデータを Anthropic ではなく顧客自身のクラウドアカウントに保存するのが最大の特徴です。

背景には、Fable 5 から導入された30日間のデータ保持があります。巧妙な悪用は無害に見える会話を複数のセッションやアカウントに分散させるため、一定期間保持して突き合わせないと検知できないというのが理由で、学習目的の保持ではないと公式に明言されています。

![分散した悪用を見つけるにはデータの保持が必要になる一方で、保持先が Anthropic だと規制業種は使いにくい](https://images.ryu-ki-learn.com/enterprise-frontier-safeguards/efs-dilemma.png)

一方で、金融や医療のような規制業種ではモデル提供者側にデータが残ること自体が採用しにくい理由になるため、このジレンマを解くために Anthropic が100社以上の顧客および AWS・Google Cloud・Microsoft Azure と共同で設計したのが EFS です。

## 従来との比較

| 観点 | 30日データ保持 | ゼロデータ保持（ZDR） | EFS |
|---|---|---|---|
| 監視用データの保存先 | Anthropic 側 | 保存しない | 顧客のクラウド |
| 時間・アカウント横断の検知 | 可能 | 不可 | 可能 |
| 検知結果を確認する人 | Anthropic 側 | 対象なし | 顧客の担当者 |
| 暗号鍵の管理 | Anthropic 側 | 対象なし | 顧客（CMEK） |

表で違うのは、時間をまたいだ監視をどう成り立たせるかの部分です。

## EFS の仕組み

EFS の動きは、データの流れを追うとわかりやすいです。

![EFS のデータの流れ。活動データは顧客のクラウドアカウントに保存され、検知シグナルは顧客のセキュリティチームに直接届く](https://images.ryu-ki-learn.com/enterprise-frontier-safeguards/efs-data-flow.png)

利用者が Claude を呼び出してモデルが応答するところまでは、EFS の有無で変わりません。EFS が関わるのはその後ろ側で、監視に使う活動データが Anthropic のストレージではなく、顧客の暗号鍵とアクセスポリシーの下にある自社クラウドのストレージに保存されます。

検知を担うのは Anthropic が運用する自動監視システムです。直近一定期間分のトラフィックを解析して、深刻な悪用の兆候を探します。公式に挙げられている対象は、攻撃的なサイバー能力や生物学的能力を開発しようとする試みと、盗まれた・漏えいした認証情報の兆候です。何かを検知すると、そのシグナル（フラグ）は Anthropic の担当者ではなく顧客に直接送られ、顧客のセキュリティチームが確認して対応を決めます。

:::note
監視システムが顧客側のストレージをどのように読み取るかといった実装の詳細は、現時点では公開されていません。図で保管先と自動監視システムを結ぶ点線がその部分です。
:::

EFS を構成する部品は3つで、いずれも必要なものだけを有効化するオプトイン方式です。

| 部品 | 役割 |
|---|---|
| 顧客所有ストレージ | 活動データを自社クラウドアカウントに保存 |
| 顧客管理の暗号鍵（CMEK） | 保存データを自社の鍵で暗号化 |
| 完全自動レビュー | Anthropic の人によるレビューを不要化 |

どれを有効にしても、モデルの挙動、API の料金、レート制限は変わりません。

## 安全に使えると言える理由

![顧客が握るもの（データの保管）と Anthropic が担うもの（検知の運用）の分担](https://images.ryu-ki-learn.com/enterprise-frontier-safeguards/efs-split.png)

EFS が安全と言える根拠は、図の左側にある「データの保管」と右側にある「検知の運用」を別の主体に分けている点にあります。

顧客側は、データの置き場所と暗号鍵、アクセスポリシーと監査ログ、そしてフラグを確認する人を自社の統制のまま握ります。新たに「信頼できるデータ委託先」を1社増やす必要がなく、特権的な法務資料や未公開情報を誰が見てよいかが厳しく決まっている規制業種でも、レビュー担当を自社の訓練済みの人にできます。

Anthropic 側は、セッションやアカウントをまたいだ悪用パターンを見つける検知の運用だけを受け持ち、顧客には判断材料を渡します。

この分担を、Wells Fargo の CISO は次のように表現しています。

> We keep custody of our data while Anthropic operates the detection. That split is what lets our teams put frontier models to work safely and meet our obligations to customers, employees, and regulators.

訳すと、「データの保管責任は私たちが持ったまま、検知は Anthropic が運用する。この分担があるからこそ、フロンティアモデルを安全に仕事に使い、顧客・従業員・規制当局への義務を果たせる」とのことです。

## 提供時期と対応プラットフォーム

| 項目 | 内容 |
|---|---|
| 提供開始 | 2026年秋から段階的に提供 |
| 対象 | エンタープライズ顧客（申請制） |
| 対応プラットフォーム | Claude Code / Claude Enterprise / Claude Platform / Amazon Bedrock / Claude Platform on AWS / Google の Agent Platform / Microsoft Foundry |
| 提供までのつなぎ | 対象顧客向けの Fable 5 と Fable 5.1 の ZDR 提供 |
| 料金（Anthropic） | 無料 |
| 料金（クラウド側） | 保存・読み書き・転送分の顧客負担 |

Amazon Bedrock 経由でも Anthropic 直接と同等の統制が提供され、活動データは自分の AWS アカウントに置けるとされています。申し込みは以下のフォームからです。

## 用語整理

| 用語 | 意味 |
|---|---|
| ゼロデータ保持（ZDR） | 処理後にデータを保存しない契約形態 |
| 30日データ保持 | 悪用の相関分析のために Fable 5 から導入された保持期間 |
| Mythos クラス | Fable 5.1 や Mythos 5.1 など最上位の高能力モデル |
| CMEK | 顧客管理の暗号鍵 |
| フラグ | 監視システムが検知した要確認シグナル |

## おわりに

EFS を追ってみて、「ゼロデータ保持と悪用検知の両立」は、データの保管と検知の運用を分けることで成り立っているのだと整理できました。個人で使う分には直接関係ありませんが、Bedrock 経由で Claude を使う企業案件では、活動データを自分の AWS アカウントに置ける選択肢として今後効いてきそうです。今秋のロールアウトで具体的な設定方法が公開されたら、また確かめてみたいと思います。
