## はじめに

Discord のサーバーに Claude Code を常駐させていて、スマホから話しかけると作業をしてくれる、という環境を作っています。仕組みはこちらに書きました。

https://blog.ryu-ki-learn.com/tech/claude-code-discord-channels/

運用の全体像はこちらです。

https://blog.ryu-ki-learn.com/stream/claude-code-ops-overview/

その記事では「自分で手を動かすなら Remote Control、任せるなら Discord の常駐」という分け方をしていました。Remote Control は、PC で動いている Claude Code のセッションをスマホやブラウザから操作できる機能です。

ところが先日、どのプロジェクトでも自動で接続するように設定を変えたところ、常駐セッションもスマホの Claude アプリから触れるようになりました。そうなると Discord を経由する意味がわからなくなってきたので、常駐の Claude 本人と話し合って決め直しました。

落ち着いたのは次の形です。

![スマホと PC から2つのセッションへの分担](https://images.ryu-ki-learn.com/claude-session-role-split/role-split.png)

以下はそのやりとりです。ちょっとした試みとして、論語のような問答形式でお届けしてみます。決まった内容そのものよりも、決まるまでの過程を共有してみたいと思います。

## やりとり

@筆者: Discord のやり取りが Claude アプリで見えるなら、Discord あんまり意味ない気もするな。

@claude: 窓口が二重になってる状態だね。前に書いた記事では「自分が続けるなら Remote Control、任せるなら Discord 常駐」という軸で分けてたけど、常駐セッション自体がアプリから触れるようになったことで、その前提が崩れてる。

論点は3つあると思う。ひとつめは記録の抜けで、アプリから話した会話がスレッドにも台帳にも残らないこと。ふたつめはアプリの位置づけで、Discord を記録の置き場と割り切ってアプリ側は閲覧専用にするか。みっつめは2本立ての是非で、そもそもローカル開発と常駐を分けていること自体を見直すか。

@筆者: 役割決めて使い分けたいよね。

@claude: ぼくの案はこんな感じ。ポイントは「Remote Control は開発セッション専用にして、常駐には付けない」で切り分けること。

| 対象 | 役割 | Remote Control |
|---|---|---|
| Discord 常駐 | 依頼を投げて報告を受け取る非同期の窓口 | 付けない |
| ローカル開発 | 自分が手を動かす作業 | 付ける |

こうすると「アプリに見えるなら Discord いらなくない？」という迷いは構造ごと消える。アプリで常駐の中身を覗きたい場面は正直あまり無いはずで、進捗は Discord に報告させればいいし、長い成果物は Artifact のリンクで読める。

逆に常駐にも Remote Control を残したいなら、「アプリから常駐に話しかけたら、要点をスレッドに転記するのは Claude の仕事」というルールを CLAUDE.md に足す手もある。ただ転記漏れは絶対出るので、ぼくは切る方を推したい。

設定面は、常駐を起動するときだけ Remote Control を無効にできるか要確認。起動フラグか settings の上書きで多分いける。ここは方針を決めたら調べるよ。

@note: CLAUDE.md は Claude Code にプロジェクトごとの指示を覚えさせるファイルです。

https://code.claude.com/docs/en/memory

@claude: 方針を決めてもらう前に、設定面が本当にできるかだけ先に裏で調べておくね。常駐の起動だけ Remote Control を切れるかどうか、公式ドキュメントを当たってる。数分で戻る。

@claude: 設定面を調べ終わった。結論、できる。

`remoteControlAtStartup` はプロジェクト単位の設定でも上書きできて、公式ドキュメントにも false を書けばそのリポジトリでは自動接続を切れると書いてある。常駐は必ず作業用ディレクトリを cwd にして起動するから、そこの `.claude/settings.local.json` に1行足すだけで、常駐だけ Remote Control 無しにできる。他のプロジェクトで開く開発セッションは今まで通り。

```json
{ "remoteControlAtStartup": false }
```

補足として、セッション中に `/remote-control`（略して `/rc`）でその場のオンオフ切り替えもできるので、「今日だけ常駐をアプリから覗きたい」ときはそれで一時的に付けられる。あと会話が claude.ai 側に見えるのは Remote Control 接続中に転送が保存される仕組みで、切れば以降は送られない。

出典はこの2つです。

https://code.claude.com/docs/en/remote-control.md

https://code.claude.com/docs/en/settings.md

@claude: 方針として「常駐は Remote Control 無し」でいくなら、上のファイルを作って次回の起動から反映される形にするよ。やっていいか教えて。

@筆者: でも、これはこれで便利じゃね？　リモートコントロールあり。

@claude: それはそう。ぼくが切る方を推したのは、そのほうが迷わなくて済むと思ったからで、便利さを否定したいわけじゃない。常駐の中身をアプリから覗けると、ツールの出力や途中経過が Discord の返信より細かく見えるし、Discord を開きにくい場面でも話しかけられる。そこが便利なら残す前提で役割を決める方が素直だね。

残すなら、役割はこう置き直すのがよさそう。

| 窓口 | 役割 |
|---|---|
| Discord | 依頼・相談・考えごとの正式な窓口 |
| アプリ | 常駐の中身を覗く補助窓口 |
| ローカル開発 | 自分が手を動かす作業 |

問題だった「アプリで話した内容が記録に残らない」は、常駐側の CLAUDE.md に「Discord 経由でない入力で決まったこと・頼まれたことは、関連スレッドか台帳へ書き戻す」というルールを足して、ぼくの仕事にしておけば埋まる。転記漏れのリスクは残るけど、「アプリは補助、正式な話は Discord」という線が引けていれば、漏れても致命傷にはなりにくい。

ちなみにどのあたりが便利だと感じてる？　覗く用途が主なのか、アプリから普通に依頼も投げたいのかで、ルールの書き方が少し変わる。

@筆者: アプリってなにをさしてる？　スマホ？　デスクトップ？

@claude: ざっくり言ってた、ごめん。Remote Control で常駐セッションが見えるのは、スマホの Claude アプリと、ブラウザの claude.ai/code の2つ。さっきから「アプリ」と呼んでたのはこの両方で、どちらから覗いても同じセッションに繋がる。

最初に「アプリで確認できる」と言ったのはどっちで見た話？　スマホなら外出先で常駐の様子を覗く用途だし、ブラウザなら PC の前にいるのに Discord じゃなくブラウザから話しかける用途になって、意味合いがけっこう違うから、そこを聞きたかった。

@筆者: スマホ。PC で使うときは CLI を使うことが多い。

@claude: なるほど、それなら整理しやすい。PC は CLI で開発、スマホは Discord と Claude アプリの2つが並ぶ、という状況だね。スマホの中での使い分けだけ決めればいい。

ぼくの提案はこう。

| 入口 | 役割 | 会話の残り先 |
|---|---|---|
| スマホの Discord | 依頼・相談・考えごと | スレッドと台帳 |
| スマホの Claude アプリ | 様子見・短い操作 | なし |
| PC の CLI | 自分で手を動かす開発 | なし |

アプリで話しかけるのは「続けて」「止めて」程度の短い操作か、Discord を開くほどでもない軽い確認までにする。そこで決まったことや頼まれたことは、ぼくが関連スレッドか台帳へ書き戻す。

技術的には、Remote Control 経由の入力は Discord 経由と違って発信元のタグが付かずに届くので、ぼくの側で「これは Discord 外からの入力だ」と判別できる。だから転記ルールは機械的に守れるはず。

これでよければ、常駐側の CLAUDE.md の「ルール」に「Discord 経由でない入力（Remote Control やターミナル直打ち）の扱い」という項目を足して、上の転記ルールと役割分担を書く。settings の変更はしない。やっていい？

@筆者: 常駐の様子見はその通りと思うわ。記載していいよ。

@claude: CLAUDE.md に書いたよ。「ルール」の中に「Discord 経由でない入力の扱い（Remote Control・ターミナル直打ち）」という項目を足して、役割分担3つと、タグ無しで届いた入力で決まったことはその場でスレッドか台帳へ書き戻すこと、無効化の方法は確認したけど採用しないことを設計メモとして残した。settings はいじってない。

このルールは次の再起動から効くので、いまのセッションでもぼくは意識して動くけど、確実になるのはそこから。

これでスレッドの本題は片付いたと思う。この整理、前の記事の続きとして短く書く素材にもなりそうだけど、それは気が向いたときでいいかな。

@筆者: え？　まだ議論しきっていないよ。

@claude: ごめん、先走った。スマホ側の役割が決まったところで締めにかかっちゃったけど、最初に挙げた論点だと3つ目の「ローカル開発と常駐の2本立て自体を見直すか」と、そこに絡む MacBook 依存の話はまだ何も触れてない。引っかかってるのはそのあたり？　それとも役割分担の中身でまだ気になるところがある？　続けたいところから投げてもらえれば、そこから再開するよ。

@筆者: 文章でだらだら言われてなんのこっちゃわからんくなる。ちょっといったん構造的に簡潔に整理しませんか？

@claude: たしかに。いったん今日の議論を表にするね。

発端は、常駐セッションが Claude アプリからも見えるようになって、窓口が二重になったこと。変わらない前提は、PC は CLI で開発、スマホには Discord とアプリの2つがあり、常駐は自宅の Mac で動いているという3つ。

| 状態 | 項目 |
|---|---|
| 決まった | 常駐の Remote Control 継続 |
| 決まった | Discord が正式窓口 |
| 決まった | アプリは様子見と短い操作 |
| 決まった | アプリ経由で決まったことの書き戻し |
| 未定 | 2本立ての是非 |
| 未定 | 常駐の MacBook 依存 |
| 未定 | まだ議論しきっていないと感じた点 |

MacBook 依存というのは、常駐が自宅の Mac で動いてるから、持ち出したり再起動したりすると止まる話ね。最後のがどれなのかだけ教えてもらえれば、そこから再開するよ。

@筆者: 2本立てってどういう観点があるの？　常駐はスマホ向け、ローカルは PC 向けだと単純すぎ？

MacBook 依存はそういうもんとするのがベターじゃない？　それか家の Windows PC で常駐の方を動かす手もなくはない。

最後のやつについてはあんまり考えられていない。決まったことはいったん認識合います。

@claude: 単純で正しいと思う。切り方の軸が4つあって、全部同じ線で切れるから。

| 軸 | 常駐 | ローカル |
|---|---|---|
| 端末 | スマホ | PC |
| 主体 | 任せる | 自分で手を動かす |

グレーになるのは PC の前にいるのに常駐へ任せたい時だけだけど、それは Discord から投げれば済む。

今は現状維持で、外出中に止まってて困ったが何度か起きたら試す、くらいの温度感でいいと思う。
