## はじめに

WebAssembly（Wasm）という言葉を目にする機会が増えてきました。ブラウザで動作するものくらいの認識（認識と言っていいのかはさておいて）はあるものの、詳細はよくわかっていませんでした。

そこでこの記事では、Wasm がどういうもので、どうやって動いているのかをざっくり整理してみます。

:::note warn
この記事は、2026年8月時点の Wasm の基本的な仕組みを整理したものです。Chrome・Firefox・Safari・Edge など、Wasm に対応した現行の主要ブラウザを前提にしています。

Wasm の基本機能は主要ブラウザで広く利用できますが、高度な機能はブラウザやバージョンによって対応状況が異なる場合があります。
:::

## WebAssembly（Wasm）とは何か

一言で言うと、Wasm は、さまざまな環境で安全かつ効率よく実行できる、低レベルなコード形式です。ブラウザでは、主に `.wasm` というバイナリファイルとして読み込まれます。

C/C++ や Rust などで書いたプログラムを Web 上で動かすための、共通のコンパイル先です。なお、ブラウザのために広く使われていますが、Wasm 自体はブラウザ専用ではありません。ブラウザ以外の環境に組み込んで使うこともできます。

https://webassembly.org/

背景には、Web 上でもゲーム・画像処理・データ分析などの負荷が高い処理を効率よく動かしたいことや、既存の C/C++ などの資産を活用したいという需要があったようです。

Wasm は W3C の標準仕様として策定されており、主要ブラウザが対応しています。そのため、特別なプラグインを追加しなくても利用できます。

https://www.w3.org/TR/wasm-core/

身近な利用例には、前述のような負荷が高い処理が行われる、画像処理・ゲーム・データ分析などがあります。例えば DuckDB-Wasm は、分析用のデータベースである DuckDB を Wasm にコンパイルすることで、ブラウザ上で動かしています。

## Wasm が動く仕組み

大きく開発者側とブラウザ側の2段階に分かれます。

開発者側では、C/C++ や Rust などで書いたソースコードを、コンパイラで Wasm のモジュールに変換します。モジュールは通常、`.wasm` という拡張子のバイナリファイルとして配布されます。

ブラウザが受け取るのは、元のソースコードではなく Wasm のモジュールです。そのため、ブラウザは元のプログラムがどのような言語で書かれたのかを意識せず、同じ仕組みで扱えます。

ブラウザ側では、次のステップで実行されます。

```text
1. .wasm ファイルを取得する
2. 内容を検証し、ブラウザのエンジンがコンパイルする
3. インスタンス化する（実行できる状態に組み立てる）
4. JavaScript からエクスポートされた関数を呼び出す
```

![Wasm がブラウザで動くまでの流れ](https://images.ryu-ki-learn.com/wasm-overview/wasm-flow.png)

https://developer.mozilla.org/ja/docs/WebAssembly

2の検証とコンパイルについて、もう少し説明すると、`.wasm` はバイナリ形式で、ブラウザのエンジンが効率よくデコード・検証し、実行環境に合わせたコードへ変換できるように設計されています。そのため、計算量の多い処理ではネイティブに近い性能を発揮できる場合があるそうです。

:::note warn
ただし、「Wasm にすれば必ず高速になる」という意味ではありません。JavaScript と Wasm の間でデータを受け渡すコストや、処理内容、ブラウザの実装などによって性能は変わります。Wasm が得意なのは、まとまった計算を繰り返し実行するような処理です。
:::

### バイナリの中身を見てみる

バイナリ形式と言われても中身が想像しづらいので、少し覗いてみます。Wasm には WAT（WebAssembly テキスト形式）というテキストの表現が用意されていて、バイナリと対応した形で読み書きできるようになっています。

2つの整数を足すだけの関数を WAT で書くと、こんな見た目になります。

```wasm
(module
  (func $add (param $lhs i32) (param $rhs i32) (result i32)
    local.get $lhs
    local.get $rhs
    i32.add)
  (export "add" (func $add))
)
```

`i32` は32ビット整数のことで、`param` が引数、`result` が返値の型宣言です。`local.get` は引数の値をスタックに積む命令で、積んだ2つを `i32.add` で足しています。最後の `export` は、この関数を `add` という名前で外から呼べるようにする宣言です。

普段書くのはあくまで C/C++ や Rust などのソースコードで、この形式を直接書く機会はあまりありませんが、`.wasm` の中身はこういう命令の列なのだという感覚は掴みやすくなるかと思います。

https://developer.mozilla.org/ja/docs/WebAssembly/Guides/Understanding_the_text_format

## JavaScript との役割分担

Wasm は JavaScript の置き換えではなく、分担相手です。

Wasm 側が担当するのは、画像処理やデータ分析などの重い計算です。一方で、Wasm 自体が JavaScript のように DOM（HTML の要素をプログラムから操作するための仕組み）を操作したり、Web API を自由に呼び出したりする機能を持っているわけではありません。必要な処理は、JavaScript などホスト側の API を介して実行します。

JavaScript 側は、UI の操作や API 呼び出しに加えて、Wasm への橋渡しを担当します。Wasm にデータを渡し、計算結果を受け取って画面に反映する、という役割分担です。

|             | Wasm                           | JavaScript           |
| ----------- | ------------------------------ | -------------------- |
| 得意なこと       | まとまった計算の繰り返し（画像処理・データ分析・3D など） | UI の組み立て、非同期処理、全体の制御 |
| DOM・Web API | 直接は触れない（ホスト側を介する）              | 直接触れる                |
| コードの用意      | C/C++・Rust などからコンパイル           | そのまま書く               |

そのため、実際のアプリは、「入口は JavaScript で、重い処理だけ Wasm に任せる」という構造になると言えるかと思います。

なお、先ほどの `add` 関数を呼ぶ場合は以下のようになります。

```javascript
WebAssembly.instantiateStreaming(fetch("add.wasm")).then((obj) => {
  console.log(obj.instance.exports.add(1, 2)); // 3
});
```

`instantiateStreaming` は、ファイルのフェッチとコンパイル、インスタンス化までを1ステップでやってくれるメソッドです。あとは `exports` から関数を取り出して、普通の JavaScript の関数と同じように呼び出せます。Wasm 側で公開した関数が、JavaScript からはただの関数として見える、という形です。

https://developer.mozilla.org/ja/docs/WebAssembly/Guides/Loading_and_running

先ほど挙げた DuckDB-Wasm もこの構造です。SQL を処理するデータベースエンジンが Wasm として動き、JavaScript が入力を受け取ってエンジンに渡し、結果を受け取ります。「ブラウザで DB が動く」というのは言い換えると、DuckDB を Wasm にコンパイルし、JavaScript から利用できるようにする、といえるかと思います。

https://duckdb.org/docs/current/clients/wasm/overview

## おまけ（実際に触ってみて）

私がこの仕組みを知った（知ろうと思った）のは、自分のブログに記事検索を付けようとしたときでした。検索のために API サーバーやマネージドの検索サービスを用意するのは大袈裟だなと思っていたところ、DuckDB-Wasm を使えばブラウザの中だけで完結すると知って試してみました。

実際に組み込んでみて印象に残っているのは、エンジン本体のサイズです。DuckDB の Wasm ファイルは30MB を超えていて、ページを開いた時点で読み込むわけにはいかないので、検索窓に触れたタイミングで遅延ロードする形にしました。

さらにデプロイの段階で、ホスティング側（Cloudflare）の「1ファイルあたり25MB まで」という上限に引っかかって止まりました。最終的にエンジン本体だけ公式配布の CDN から取得する形に変えたのですが、その際、Wasm も結局はただのファイルなんだなと感じました。複雑な仕組みが裏で動いているというより、バイナリを1つ配って、ブラウザがそれを受け取って実行しているといったイメージを持てるようになりました。

## おわりに

以上、簡単ではありましたが、Wasm について調査・整理してみました。

Wasm はさまざまな環境で実行できる低レベルなコード形式で、ブラウザでは `.wasm` ファイルとして読み込まれます。JavaScript と分担しながら重い計算を担当することで、DB エンジンのようなソフトウェアもブラウザの中で動かせる、という仕組みでした。
